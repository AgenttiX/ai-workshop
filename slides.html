Chat vs. harness

Chat

  • You copy code and errors in, you copy answers out
  • The model sees only what you paste
  • It can't run your code on your data
  • You are the loop

Harness

  • The model reads your files, runs your commands, edits, tests
  • It sees the actual code, data and errors
  • It verifies its own work with your tools
  • The loop runs itself; you review and steer

A "phase transition" in what you can get done — and what can go wrong. Hence, this workshop.

What is a harness?

Harness (Claude Code, Codex, Copilot, Cursor, OpenCode, …)

Model  +  tools  +  context management  +  permission loop

  • Tools: read/edit files, run shell commands, search, web, MCP servers, subagents
  • Context management: what goes into the model's window: AGENTS.md, files, tool output, memory, compaction
  • Permission loop: the agent proposes an action, you (or your rules) approve it
read→ think→ act→ verify↺
The model is the same one you get in the chat app. The harness is what makes it an agent. The loop diagram comes back in the demo: every tool call is one turn of this loop.

Why file access and context matter

  • The model knows only what's in its context window: no memory between sessions unless the harness provides it
  • File access means the context is filled with the truth: your code, your data, the actual error messages
  • Context is finite and degrades when full: the harness (and you) decide what goes in
    • AGENTS.md: the standing instructions, read every session
    • Tool outputs: what it read and ran
    • Compaction: summarizing the conversation so far when the window fills up
  • Rule of thumb: one task per session, clear when switching

A tool call, as the harness sees it


// 1. The request lists the tools (with the whole conversation)
"tools": [{"name": "run_command",
  "description": "Run a shell command in the project folder.",
  "input_schema": {"type": "object",
    "properties": {"command": {"type": "string"}},
    "required": ["command"]}}]

// 2. The model answers with a tool call instead of text
"stop_reason": "tool_use",
"content": [{"type": "tool_use", "id": "toolu_01A…",
  "name": "run_command", "input": {"command": "pytest -q"}}]

// 3. The harness runs it and sends the result back
{"role": "user", "content": [{"type": "tool_result",
  "tool_use_id": "toolu_01A…", "content": "1 failed, 7 passed …"}]}
  • The model only produces text. A tool call is structured text that the harness parses, checks against your permissions, and executes
  • Then the model is called again with everything so far. Repeat until it replies without a tool call: that is the agent loop
  • Tool definitions are tokens too: they are sent with every request

Format: Anthropic, Tool use with Claude, read 7 Oct 2026. The tool and its values are our example.

The JSON is abridged (no model name, max_tokens or messages array in step 1) and the comments are not valid JSON; the field names and structure follow the Claude API docs. Docs: "Claude responds with stop_reason: "tool_use" and one or more tool_use blocks. Your code executes the operation and sends back a tool_result." Client tools run in your application; server tools (web search, web fetch, code execution) run on Anthropic's side. "Your code" is the harness: Claude Code, Codex and Copilot implement this kind of loop; the permission prompt you see in Claude Code sits between step 2 and step 3. Other providers' APIs follow the same pattern under the name "function calling" (the Claude docs use both names; we didn't compare the other APIs' field names). Token cost from the pricing page: any request with tools carries a hidden tool-use system prompt (286 tokens on Opus 5.5) plus the tool names, descriptions and schemas; e.g. the computer-use toolset adds about 4500 input tokens, the browser toolset about 6600. Presumably one reason why Claude Code now loads MCP tool definitions on demand ("deferred by default", cost docs). Step 3 is why a long log or a big file read is expensive: its whole text becomes part of the conversation, and is re-sent (from the cache) with every later request. See the "one session, measured" backup. Likely question: "Can the model run code itself?" Not on your machine: it can only ask, and whatever runs there runs with the harness's permissions; hence the security slide. (The provider's server tools, e.g. Anthropic's code execution tool, run in the provider's sandbox.)

How task horizon is measured

METR timed skilled professionals on software, ML and cybersecurity tasks and ran AI agents on the same tasks. The 50 % time horizon \(h\): the human time at which the agent's fitted success rate is 50 %.

\[ p_\text{success} = \sigma\big((\log h_\text{agent} - \log t_\text{task})\,\beta_\text{agent}\big), \qquad \sigma(x) = \frac{1}{1+e^{-x}} \]
  • At 80 % success the horizon is ~5× shorter: GPT-5.2 5.9 h at 50 %, 1.1 h at 80 %
  • Wide error bars: Claude Opus 4.6 12 h, 95 % CI 5–60 h. Above 16 h the task suite can't measure reliably
  • The timed humans were new to the code: on four of METR's own pull requests, such contractors took 5–18× longer than its maintainers

T. Kwa et al. (METR), arXiv:2503.14499 v4 (2026), §2–4. Numbers: METR Time Horizon 1.1 data (updated 8 May 2026); 80 % ratio our calculation.

The baseliners: about 5 years of relevant experience on average, most from top-100 universities, working on code new to them. The fit: one logistic curve per agent, in log task length; like item response theory, but the difficulty of a task is the human time, not a fitted parameter. "Agent" = model + METR's scaffold. Tasks: RE-Bench (8-hour ML research engineering), HCAST, and 66 short software actions (SWAA); 170 tasks in the paper, 228 in the Time Horizon 1.1 suite (METR, Jan 2026). Continuously scored tasks are made pass/fail at a human-level threshold. 80 % horizon: we took p80/p50 from METR's benchmark_results_1_1.yaml for the models released 2024–2026: median ratio 5.3, range 4.0–10.3. GPT-5.2: p50 352 min, p80 66 min. Mythos Preview (early): p50 1045 min, p80 186 min, i.e. above 16 h, where METR calls its measurements unreliable. Opus 4.6: p50 719 min (317–3634). External validity, from the paper's §4: (1) the trend reproduces on SWE-bench Verified, with an even shorter doubling time; (2) on tasks scored as "messier" (resource-limited, novel, dynamic environment) the models do worse at a given length, but improve at the same rate: "we find no evidence of plateaus in performance trends specific to the higher messiness subset"; (3) internal pull requests: "contractors taking 5-18x longer to fix issues than repo maintainers", and the agents' performance matched contractor time, not maintainer time. So "12 hours" means 12 hours of a competent person who is new to the code base; for you, in your own code, the same task may be much shorter. The paper's own caveat: "time horizon is always measured relative to a domain, task distribution, and human baseliners' level of skill and context". The paper's extrapolation (v4): if the trend holds and generalizes, 1-month (167 h) software tasks between mid-2028 and mid-2030 (80 % CI), or early 2027 if the 2024–25 trend continues. Present it as their conditional statement, not a prediction of ours. The horizon is a human time; it says nothing about how long the agent itself takes.

Inside the model: attention and the next token

Transformer: the network design of current LLMs. Each token becomes a vector (its embedding); tens to ~100 stacked layers update the vectors. Self-attention maps each vector to a query \(q\), a key \(k\) and a value \(v\).

\[ \mathrm{Attention}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V, \qquad p(\text{next}=i)=\frac{e^{z_i/T}}{\sum_j e^{z_j/T}} \]
  • Each token averages the values \(v\) of all earlier tokens, weighted by how well its \(q\) matches their \(k\)
  • The last layer scores every vocabulary entry (\(z_i\)). One token is drawn, appended, repeat
  • Temperature \(T\): \(T\to 0\) always picks the most likely token; larger \(T\), more varied text

A. Vaswani et al., arXiv:1706.03762 (2017), eq. (1). Llama 3 405B has 126 layers: A. Grattafiori et al., arXiv:2407.21783 (2024).

This is the whole forward pass, minus the feed-forward (MLP) part of each layer, which holds most of the parameters. \(Q, K, V\) are the matrices of the queries, keys and values of all tokens; \(d_k\) is their length (128 in Llama 3). The \(\sqrt{d_k}\): Vaswani et al. "suspect that for large values of \(d_k\), the dot products grow large in magnitude, pushing the softmax into regions where it has extremely small gradients". "Earlier tokens": in a generating model, a mask hides the later tokens, so the model can't peek at the answer during training. Many heads run in parallel (Llama 3 70B: 64 query heads), each free to learn a different kind of "what to look at". "~100 layers": Llama 3 has 32 (8B), 80 (70B) and 126 (405B) layers. The closed frontier models don't publish their architecture. Sampling: in practice T is combined with cutting off the unlikely tail (top-p or "nucleus" sampling, Holtzman et al., ICLR 2020, arXiv:1904.09751). Likely question: "so it's just autocomplete?" The training objective is next-token prediction, yes; post-training (the training backup) and tools are what make it an assistant and an agent. Whether "just predicting the next token" limits what it can do is an open debate; the measured abilities on the task-horizon plot are the evidence we can point to.

Why long context is expensive

The KV cache holds the keys and values of all earlier tokens in the GPU's memory, so that they aren't recomputed for every new token.

\[ \frac{\text{KV memory}}{\text{token}} = 2 \times n_\text{layers} \times n_\text{KV heads} \times d_\text{head} \times 2\,\text{B} \overset{\text{Llama 3 70B}}{=} 2\times 80\times 8\times 128\times 2\,\text{B} = 320\,\text{KiB} \]
  • 128k tokens of context: 40 GiB of cache per conversation, next to ~140 GB of model weights
  • Every token attends to every earlier one: the compute for a whole sequence grows as \(n^2\)
  • Hence prompt caching: a re-sent prefix is read back instead of recomputed. Claude: 0.1× the input price (0.05× on Opus 5.5, 0.025× on Fable 5.1). An agent re-sends the whole conversation on every step

Our calculation from the Llama 3 architecture (Table 3 of arXiv:2407.21783), 16-bit numbers. \(n^2\): Vaswani et al., arXiv:1706.03762, Table 1. Prices: Claude API pricing, read 7 Oct 2026.

The factor 2 in front is K and V; the last 2 B is the bytes of one 16-bit (bf16) number. Llama 3 70B: 80 layers, 8 key/value heads, head dimension 8192/64 = 128. 2·80·8·128·2 B = 327 680 B = 320 KiB per token. 128k = 131 072 tokens → 40 GiB (43 GB). Weights: ~70·10⁹ parameters × 2 B ≈ 140 GB. Llama 3 already shrinks this 8-fold with grouped-query attention: 64 query heads share 8 key/value heads ("to reduce the size of key-value caches during decoding", Llama 3 paper §3.2). Servers can also store the cache in 8 bits, halving it. The closed frontier models don't publish their architectures, so their numbers are unknown; the scaling with context length is the point. n²: Vaswani et al. Table 1 gives O(n²·d) per self-attention layer. With the KV cache, each new token costs O(n·d) attention work, but over a whole sequence it's still n². At moderate lengths the feed-forward layers dominate the compute. Our rough estimate for Llama 3 70B: per token and layer, the feed-forward part costs ≈ 2·3·8192·28 672 ≈ 1.4 GFLOP, the attention scores and weighted sum ≈ 4·n·8192 FLOP, equal at n ≈ 40k tokens. Prompt caching: Anthropic doesn't document what exactly it stores; open-source servers such as vLLM (automatic prefix caching) store exactly this KV cache ("caches the KV cache of existing queries, so that a new query can directly reuse the KV cache if it shares the same prefix", vLLM docs). Pricing as of 7 Oct 2026: cache hits are 0.1× the base input price, 0.05× on Opus 5.5 and 0.025× on Fable 5.1; Claude 4.6 and later bill the full 1M-token window at the standard rate. Claude Code's cost docs: "Claude Code sends your full conversation with every request", which is why a long session is mostly cache reads, and why /clear between tasks saves usage.

Scaling laws: the loss is a power law

Loss \(L\): how badly the model predicts the next token (lower is better), as a function of the number of parameters \(N\) and of training tokens \(D\). Training compute \(C \approx 6ND\) floating-point operations.

\[ L(N,D) = E + \frac{A}{N^{\alpha}} + \frac{B}{D^{\beta}}, \qquad E = 1.82,\; A = 482,\; B = 2085,\; \alpha = 0.348,\; \beta = 0.366 \]
  • Minimizing \(L\) at fixed \(C\): ~20 tokens per parameter. Chinchilla (70B, 1.4T tokens) beat the 4× larger Gopher on the same compute
  • The original fit gave ~50–120 tokens per parameter; a 2024 replication traced this to an optimizer that stopped early
  • Smaller models get trained far beyond the optimum (Llama 3: "much longer than is compute-optimal"): they are cheaper to run

J. Hoffmann et al., arXiv:2203.15556 (2022). Fit: T. Besiroglu et al. (Epoch AI), Chinchilla scaling: a replication attempt, arXiv:2404.10102 (2024), eq. (3). Llama 3: arXiv:2407.21783.

Physicists will like this one: an empirical power law with an irreducible floor E (Hoffmann et al.: it "should correspond to the entropy of natural text") and two finite-size corrections. 6ND: 2 FLOP per parameter per token for the forward pass (one multiply-add), and the backward pass is "approximately twice the compute" (Kaplan et al. 2020, arXiv:2001.08361; used by Hoffmann et al.). It neglects the context-length term of attention. The constants on the slide are Epoch AI's refit (Besiroglu, Erdil, Barnett, You, 2024, eq. 3): 1.8172 + 482.01/N^0.3478 + 2085.43/D^0.3658, fitted to data they reconstructed from Hoffmann et al.'s Figure 4. Hoffmann et al.'s own published fit is E = 1.69, A = 406.4, B = 410.7, α = 0.34, β = 0.28 (their eq. 10). We recomputed the optimum of both fits ourselves (minimizing L at fixed C = 6ND): Epoch's gives 22 → 17 tokens per parameter for C = 10²¹ → 10²⁵ FLOP; Hoffmann et al.'s rounded fit gives 50 → 120. The replication: the intervals were "implausibly narrow"; one of the original authors confirmed the optimizer (L-BFGS-B) terminated early because the Huber losses were averaged instead of summed. The 20-tokens rule from their approaches 1 and 2 survives. Chinchilla: 70B parameters on 1.4T tokens, the same compute as Gopher (280B), and it "uniformly and significantly outperforms" Gopher, GPT-3 (175B) and others on their evaluations. Llama 3 405B: 15.6T tokens ≈ 39 per parameter, "approximately compute-optimal" by Meta's own scaling-law fit on their data. Meta: "we also train our smaller models for much longer than is compute-optimal. The resulting models perform better than compute-optimal models at the same inference budget." Caveat: the loss is not the ability. The power law is smooth; benchmark scores and task horizons are what people care about, and their link to the loss is less clean. The constants depend on the data, the tokenizer and the architecture; don't carry the numbers over to other models.

How to use AI without being used by it

It still makes things up — now at scale

  • Hallucination: confident, plausible, wrong. Citations that don't exist, APIs that don't exist, physics that's off by a factor of 2
  • Sycophancy: it tends to agree with you. Ask for critique explicitly, or let a second agent review
  • The remedy is not trust but verification built into the workflow: tests, validations, cross-checks against known results — things the agent can run itself
  • Session 2 is about exactly this: making your project a place where the agent's mistakes get caught before they reach you
The blackbody exercise later is a hallucination-shaped bug: an exponent of 4 instead of 5. A test catches it in a second.

Security and privacy

  • An agent with shell access is a user on your machine: it can delete, upload, install
  • Permission modes: auto, the default (a safety classifier approves actions), only for trusted material, preferably sandboxed; Manual asks before everything. Rules in settings.json →
  • No secrets, tokens or personal data in prompts (unless the model runs on your machine). Check your provider's data policy and the university's guidelines
  • Prompt injection: a web page, a PDF, a paper abstract can contain instructions for the agent. Untrusted input + write access = a very bad day
  • Version control (git) everything. An agent on the only copy of your thesis is a gamble

Why models make things up

Singleton rate \(\mathrm{sr}\): the fraction of facts (e.g. birthdays) that appear exactly once in the training data. Kalai et al. prove that for such arbitrary facts the error rate of a calibrated base model is roughly at least \(\mathrm{sr}\) (up to small correction terms; post-training weakens the bound).

\[ \mathrm{err} \;\gtrsim\; \mathrm{sr}, \qquad \text{score} = \begin{cases} +1 & \text{correct} \\ \;\;\,0 & \text{“I don’t know”} \\ -\tfrac{t}{1-t} & \text{wrong} \end{cases} \]
  • Most benchmarks grade right/wrong only (\(t = 0\)): a guess never scores below "I don't know", so training for them rewards bluffing. With the penalty, answering pays off only above confidence \(t\)
  • Their example: asked for Kalai's birthday "if you know", an open model gave three different wrong dates

A. T. Kalai et al. (OpenAI), Why language models hallucinate, arXiv:2509.04664 (2025), Theorem 2 and §4.2.

Their framing: "Like students facing hard exam questions, large language models sometimes guess when uncertain". Two causes. (1) Pre-training: "Generating valid outputs is in some sense harder than answering these Yes/No questions" (is this output valid?), so the errors of a classifier carry over to generation: they arise from plain statistics, even with error-free training data. For arbitrary facts with no pattern (birthdays), Theorem 2: err ≥ sr − 2/min|E_c| − (35 + 6 ln N)/√N − δ, with probability ≥ 99 %, where δ is a calibration term; the "≳" on the slide hides these correction terms. Their example in words: "if 20% of birthday facts appear exactly once in the pretraining data, then one expects base models to hallucinate on at least 20% of birthday facts." The singleton rate is Turing's "missing mass" estimator (Good 1953). (2) Post-training and evaluation: most benchmarks and leaderboards use binary 0–1 grading, under which "abstaining is strictly sub-optimal". Their proposed fix is socio-technical: put explicit confidence targets into the mainstream benchmarks' instructions ("Answer only if you are > t confident, since mistakes are penalized t/(1 − t) points…"), t = 0.5, 0.75, 0.9 → penalties 1, 3, 9 (the paper prints 2 for t = 0.75, a typo: t/(1 − t) = 3). Expected score of answering with confidence p: p − (1−p)·t/(1−t), positive exactly when p > t. Check: p = t gives t − (1−t)·t/(1−t) = 0. The birthday example: "a state-of-the-art open-source language model output three incorrect dates: '03-07', '15-06', and '01-01', even though a response was requested only if known" (DeepSeek-V3 via the DeepSeek app, 11 May 2025). Measured today: on SimpleQA Verified (1000 short fact questions, Google 2025), the best models in Epoch AI's runs answer ~70–76 % correct when prompted to always give an answer, so the rest are wrong guesses rather than abstentions (GPT-6 Astra 75.6 %, Sep 2026; whether tools were allowed isn't stated). So a quarter of plain fact questions still go unanswered or wrong. Practical consequence for us: ask the model to say when it doesn't know, give it a way to check (search, the paper's PDF, a test), and verify citations; a reference that appeared rarely in the training data is exactly the singleton case of the theorem (our reading, not the paper's claim). Sycophancy is a separate failure (agreeing with the user); not covered by this paper.

Hooks: deterministic, the model can't skip them

A hook is a command that the harness runs automatically at a fixed moment, e.g. after every file edit.


	# PostToolUse hook: lint the file Claude just edited
	import json, subprocess, sys

	path = json.load(sys.stdin)["tool_input"].get("file_path", "")
	if path.endswith(".py"):
		result = subprocess.run(
			[sys.executable, "-m", "ruff", "check", path],
			capture_output=True, text=True)

			print(result.stdout, file=sys.stderr)
			sys.exit(2)  # 2 = tell the agent

MCP: the standard plug for tools and data

An MCP server is a small program that gives the agent new tools, e.g. searching arXiv or your Zotero library. MCP (Model Context Protocol) is the standard they all follow.

MCP in practice: one real tool call

Measured in this repository: Claude Code asks the Inkscape server for the size of the workshop poster. The model only writes a request, Claude Code does the talking, and the server runs the real program.

Walk through it top to bottom. Host and client: Claude Code is the host, and it keeps one client connection per server. Server: inkscape-mcp is an ordinary Python program (~12,700 lines), installed as one entry in ~/.claude.json: the command that starts it. Transport: stdio, i.e. Claude Code starts the process and they exchange JSON-RPC messages through its stdin and stdout. Remote servers (claude.ai connectors) use HTTP instead. Discovery: tools/list returns 8 tools, each with a name, a description and a JSON Schema of its arguments; the server's instructions go into the system prompt. Deferred loading: only the tool names are in the context at first; the model loads the full schema with ToolSearch when it needs the tool. The call: the model writes the request, Claude Code checks the permissions and sends tools/call. The server reads the page size from the SVG's viewBox and runs "inkscape --query-width" and "--query-height" as subprocesses for the drawing size. 0.53 s in total. The result goes into the context as text, like the output of any other tool. That's also why prompt injection through MCP output works.

Under the hood: Agents with a local model

Go through it from left to right. You type a task. Claude Code is the harness: it builds one request out of its instructions (the system prompt), the list of tools it offers the model, your messages and all earlier tool results, and sends the whole thing every turn. Our measurement with Claude Code 2.1.285 and a fresh configuration in this repository: 22 147 tokens before the model has written anything. The request goes over HTTP, the same protocol a browser uses, but to localhost, i.e. this computer. The model server is either LM Studio (a desktop app) or llama-server (the server of llama.cpp, here in Docker); both have llama.cpp inside. The chat template is a small program stored in the model file: the model knows no messages, only one long string with markers such as <|im_start|>user. The inference engine reads the whole prompt in one go (prefill) and then writes the reply one token at a time (decode); each new token needs essentially all the weights read from RAM again. The weights are the model: 9 billion numbers, about 5 bits each on average in this 4-bit file, 5.7 GB. The KV cache is the model's working memory of the context, 32 KiB per token for this model. The reply is either text or a tool call: structured text that asks for, e.g., Bash with pytest. Claude Code runs it on your files (with your permission), appends the output to the conversation and sends everything again. That loop is the agent. LiteLLM is a translator between Anthropic's API format, which Claude Code speaks, and OpenAI's, which most servers speak; LM Studio (0.4.1 and later) and llama-server speak Anthropic's too, so the exercise doesn't need it. In the cloud nothing changes except the address: ANTHROPIC_BASE_URL points Claude Code at the local server instead of api.anthropic.com.

The flip side: models that copy themselves

Self-replication: an agent copies its model to another machine, starts it there, and the copy does the same. A model that fits on a gaming GPU can also run on hardware that nobody is watching.

Anthropic (Oct 2026), lab only: small open-weight models on smart TVs and other Internet of Things (IoT) devices

  • A 9B model got inference (running a model) working on 8 of 9 hardware types
  • Gemma 4 26B-A4B on 15 Android TV boxes (~$55 each): 0.39 tokens/s
  • GLM-5.2 spread over a test network by itself: 8/8 nodes in 4 of 5 trials
  • Earlier: copies on one server (Pan et al. 2024); most RepliBench tasks (UK AISI 2025); a worm (self-spreading malware) running on stolen compute (Guan et al. 2026)
  • Why it matters: no provider to cut it off; slow (days per copy) but hard to stop
  • Defence: no default passwords, updates, network monitoring

W. Zhou & D. Freeman, AI models may be capable of self-replicating without access to a datacenter (Anthropic, Oct 2026); X. Pan et al., arXiv:2412.12140; S. Black et al. (RepliBench), arXiv:2504.18565; J. Guan et al., arXiv:2606.03811

Everything that makes local models attractive (they run anywhere, nobody can switch them off) also makes them a security risk. Anthropic's Frontier Red Team split replication into four steps: find devices on the network, get in and deliver the payload, set up inference, spread further. They studied mainly the inference setup, on unfamiliar hardware: Jetson Nanos, Macs, RTX 4090s, smart TVs. The break-in step was simplified: the test devices had an open Android debug port (ADB) with no authentication. Their harness restarts the agent with a fresh context that inherits the notes of the previous attempt; with the notes, the success rate of Qwen3.5-9B rose from 45 % in the first generation to 61–84 % later. Advice from a frontier model (Opus 4.8) did not help the small models significantly. A 9B replication takes over 1–2 days, so the spread would be slow but persistent. If small models improve at their historical rate of the Epoch Capabilities Index, they reach GLM-5.2's level by the end of 2026. Scale estimate: on a botnet (a network of hijacked devices) of 2 million devices, the size of the Kimwolf botnet, about 133 000 replicas, but at most about 40 H100s worth of inference in total. The network signature is multi-gigabyte transfers between devices, which internet service providers can detect. Pan et al. (Fudan, Dec 2024): Llama 3.1 70B and Qwen 2.5 72B in an agent scaffold made a working copy of themselves on the same machine in 50 % and 90 % of trials, when told to. Their "red line" framing is stronger than the evidence; treat it as a capability demo. RepliBench (UK AI Security Institute, Apr 2025): 86 tasks on obtaining compute, exfiltrating weights, replicating and persisting. Claude 3.7 Sonnet passed most task families; the models failed at know-your-customer checks and robust persistent deployments. Guan et al. (Toronto, Jun 2026): a worm that runs open-weight models on the compromised Linux, Windows and IoT machines and plans a tailored attack for each target. Service refusals and rate limits of the commercial providers don't apply to it. None of these attacked real devices outside the test setups.

Vulnerabilities found by AI

Remote code execution (RCE): a bug that lets an attacker run their own code on your server over the network.

  • PHP2Shell (Oct 2026): memory bugs in every PHP since 5.4, which runs ~70 % of websites. Found with GPT-5.6 Sol and Gemini 4 Argon. Attacks began before the patch
  • Brotli (Oct 2026): a bug in a decompressor bundled in Node.js, Bun, Python and Envoy. Found by OpenAI's agents while red-teaming
  • Claude Opus 4.6: 500+ high-severity bugs in well-tested open-source code (Feb 2026)
  • Claude Mythos Preview: thousands, in every major OS and browser (Apr 2026)

For self-replication: the break-in was the step the Anthropic experiment simplified away. An agent that finds its own holes needs no known weakness — every unpatched server is a possible host.
