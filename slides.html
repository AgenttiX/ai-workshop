The state of AI in 2026

What changed, and why it matters for how you work

Hippe, ~15 min. For those who haven't followed the last 2–3 years: facts first.

A short timeline

2022ChatGPT: chat with a language model
2023GPT-4, Claude 2: useful for text and code snippets. You paste, it answers.
2024Tool use, 100k–200k token contexts, first coding agents (Cursor, Claude Code preview)

The step that most scientists have missed: from chat to agents with access to your files and tools.

Models today

  • Cloud frontier models: Claude 5 (Fable 5.1, Opus 5, Sonnet 5), Haiku 4.5; OpenAI's and Google's frontier models
  • Open-weight models you can run yourself: Gemma 4, Qwen 3.8, and larger ones (Kimi, DeepSeek) that need a server — roughly 1–2 years behind the frontier
  • Context windows of up to ~1M tokens: your whole code base, or a paper's LaTeX plus the analysis, in one session
  • Reasoning: the model "thinks" before answering; you can trade time for quality
  • Tools: the model can call functions — read a file, run a command, search the web
Don't spend long here. The point is: several capable providers, plus open models as a real alternative (Mika's showcase).

Chat vs. harness

Chat

  • You copy code and errors in, you copy answers out
  • The model sees only what you paste
  • It cannot check anything
  • You are the loop

Harness

  • The model reads your files, runs your commands, edits, tests
  • It sees the actual code, data and errors
  • It verifies its own work with your tools
  • The loop runs itself; you review and steer

Order-of-magnitude difference in what you can get done — and in what can go wrong. Hence this workshop.

What is a harness?

Harness (Claude Code, Codex, Copilot, Cursor, OpenCode, …)

Model  +  tools  +  context management  +  permission loop

  • Tools: read/edit files, run shell commands, search, web, MCP servers, subagents
  • Context management: what goes into the model's window: AGENTS.md, files, tool output, memory, compaction
  • Permission loop: the agent proposes an action, you (or your rules) approve it
read→ think→ act→ verify↺
The model is the same one you get in the chat app. The harness is what makes it an agent. The loop diagram comes back in the demo: every tool call is one turn of this loop.

Why file access and context matter

  • The model knows only what's in its context window: no memory between sessions unless the harness provides it
  • File access means the context is filled with the truth: your code, your data, the actual error message
  • Context is finite and degrades when full: the harness (and you) decide what goes in
    • AGENTS.md: the standing instructions, read every session
    • Tool outputs: what it read and ran
    • Compaction: summarizing the history when the window fills up
  • Rule of thumb: one task per session, clear when switching

Honest caveats

How to use AI without being used by it

Mika, ~10 min including Q&A. Showing the downsides is what gives us credibility.

It still makes things up — now at scale

  • Hallucination: confident, plausible, wrong. Citations that don't exist, APIs that don't exist, physics that's off by a factor of 2
  • Sycophancy: it tends to agree with you. Ask for critique explicitly, or let a second agent review
  • The remedy is not trust but verification built into the workflow: tests, type checks, cross-checks against known results — things the agent can run itself
  • Session 2 is about exactly this: making your project a place where the agent's mistakes get caught before they reach you
The blackbody exercise later is a hallucination-shaped bug: an exponent of 4 instead of 5. A test catches it in a second.

Security and privacy

  • An agent with shell access is a user on your machine. It can delete, upload, install.
  • Permission modes: ask for everything, allow-list the safe commands, "auto" for sandboxed work only
  • Never paste secrets, tokens or personal data into a prompt. Check your provider's data policy and the university's guidelines
  • Prompt injection: a web page, a PDF, a paper abstract can contain instructions for the agent. Untrusted input + write access = a bad day
  • Version control everything. An agent on the only copy of your thesis is a gamble

Cost, limits, and your own understanding

  • Cost: subscriptions have usage quotas; agents burn tokens fast. Local models are the free-but-slower fallback
  • Skill atrophy: "How do I keep understanding the physics when the AI writes the code?"
    • Let it do the mechanical parts. Read everything before it goes into a paper.
    • Ask it to explain. Ask it to teach. Make it show the derivation.
    • Decide deliberately what you want to keep doing by hand
  • Incentives: if this is an order of magnitude, "AI or perish" is coming. We don't have an answer. We have a coffee break.
  • Which provider? Ethical, legal and practical considerations differ. Know them; make a choice; revisit it

The task

Planck's law, and a test based on Wien's displacement law:


def spectral_radiance(wavelength, temperature):
    """B_λ(λ, T), the spectral radiance of a black body per unit wavelength."""
    x = H * C / (wavelength * K_B * temperature)
    with np.errstate(over="ignore"):
        return 2 * H * C**2 / wavelength**4 / np.expm1(x)

\( B_\lambda(\lambda, T) = \frac{2 h c^2}{\lambda^5} \frac{1}{e^{hc / (\lambda k_B T)} - 1} \qquad \lambda_\text{max} T = b = 2.898 \times 10^{-3}\ \text{m K} \)

The loop, made visible

read the test & code→ reason→ edit→ run pytest↺
  • Every tool call is a permission decision: read (usually free), edit (you review), run (you approve)
  • If the tests pass, it stops. If not, it goes around again. It's verifying itself with your tools.
  • Watch for: did it read before editing? Did it run the tests, or just claim success?

Four things you control

1. The task

  • Specific, verifiable, small enough to review
  • Say what "done" means: "and run the tests"
  • Plan mode for anything non-trivial

2. The context

  • AGENTS.md / CLAUDE.md: standing instructions
  • /context to see, /compact to shrink, /clear to reset
  • One task per session

3. The permissions

  • Default: ask. Allow-list the safe commands in .claude/settings.json
  • Auto mode only in a sandbox or a throwaway repo

4. The verification

  • Tests, linters, type checkers: the agent's feedback signal
  • Git: every change reviewable and reversible
  • You read the diff. Always.

AGENTS.md: the file the agent reads every session


# AGENTS.md

## Commands
- Run tests: `pytest`
- Lint: `ruff check`
- Type check: `pyrefly check`

## Project structure
- `exercises/`: starters, deliberately imperfect
- `solutions/`: reference solutions, tested in CI

## Code style
- Python 3.12 type hints, Sphinx docstrings
  • Put in: commands, structure, conventions, what not to touch, where the docs are
  • Leave out: anything it can read from the code. It costs context on every session
  • /init writes a draft. The valuable part is what only you know
  • AGENTS.md is the tool-agnostic name; CLAUDE.md containing @AGENTS.md points Claude Code to it

Permissions


{
  "permissions": {
    "allow": [
      "Bash(pytest:*)",
      "Bash(ruff check:*)",
      "Bash(pyrefly check:*)",
      "Bash(git status:*)"
    ]
  }
}
  • .claude/settings.json in the repository (shared with the group) or ~/.claude/settings.json (personal)
  • Safe to allow: tests, linters, read-only git. Keep the prompt for: installs, network, deletion, git push
  • Modes: default (ask) → accept edits → plan (read-only) → auto (sandboxed, for the brave)

Hooks: deterministic, the model can't skip them


#!/usr/bin/env bash
# PostToolUse: lint the edited file
FILE=$(python3 -c 'import json,sys;
  print(json.load(sys.stdin)["tool_input"]["file_path"])')
[[ "$FILE" == *.py ]] || exit 0
if ! OUT=$(ruff check "$FILE" 2>&1); then
  echo "$OUT" >&2
  exit 2   # 2 = block and tell the agent
fi
  • Events: PreToolUse, PostToolUse, Stop, SessionStart, notifications, …
  • The hook gets the tool call as JSON on stdin; exit code 2 feeds stderr back to the agent
  • Use for: formatting, linting, secret scanning, notifications, "don't stop until the tests pass"
  • The Stop hook is how Hippe's research loop keeps the agent going (showcase)

Demo: ask for sloppy code with unused imports → the hook complains → the agent fixes it unasked.

Subagents: specialists with their own context


---
name: physics-reviewer
description: Reviews scientific Python code for
  physics and numerical correctness. Use after
  changing code that implements equations.
tools: Read, Grep, Glob, Bash
model: sonnet
---
You are a careful physicist reviewing code.
Check units, equations, limits, error
propagation, numerics and tests. Report:
verdict, findings (most serious first),
missing tests. Do not praise the code.
  • Fresh context per agent: the noise of reading 40 files stays out of your main session
  • Parallel: several reviewers, several explorations at once
  • Restricted tools and a cheaper model where appropriate
  • Built-in: Explore, Plan, general-purpose. Custom: yours
  • Cost: each starts from zero. Use for "long investigation, short report"

Then, in a session:

  • Servers exist for arXiv, Zotero, GitHub, databases, Slack, lab instruments, your wiki, …
  • Trust: the server runs on your machine and its output enters the context. Prompt injection through a paper abstract is a real thing
  • --scope project writes .mcp.json: the whole group shares it

Beyond the IDE: worktrees, headless, CI, plugins

  • Git worktrees: several sessions on the same repository, each on its own branch and directory. Claude Code can create them for you (claude --worktree)
  • Headless: claude -p "summarize the failing tests" in a script, a cron job, a pipeline
  • CI: Claude Code as a GitHub Action: review PRs, fix failing builds, triage issues
  • Plugins and marketplaces: skills, agents and hooks bundled and shared. Hippe's claude-loadout is one install.sh away
  • /insights: what have I been asking for repeatedly? → turn it into a skill

Making your project AI-ready

So that the agent fixes its own mistakes before you see them

Mika, 20 min. Based on the unit testing & CI/CD lecture. Demo: exercise 04.

The agent needs a feedback signal

  • Without tools, an agent can only believe its code works. With tools, it can check.
  • Everything you'd do for reproducible research code helps twice as much now:
PillarToolWhat it gives the agent
Unit testspytest"Does the physics still hold?" Regression tests from current output + literature values
LintingruffStyle and bug patterns, in milliseconds
Type checkingpyreflyWrong shapes, units-as-types and arguments across the whole code base
CIGitHub ActionsThe same checks on every push, including the agent's
Packaging & READMEpyproject.tomlThe agent can install and run the project from the instructions alone
The thesis of this block: tests, lint, types and CI are the agent's senses. A project without them is an agent working blind.
